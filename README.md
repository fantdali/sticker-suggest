# Интеллектуальная система подбора и генерации стикеров

## 1. Постановка задачи

Цель проекта - собрать работающий пайплайн, который по текстовому запросу подбирает подходящие стикеры из базы. Если в базе нет достаточно хорошего варианта, система может дополнительно сгенерировать новый стикер. По сути это задача мультимодального поиска: нужно сравнивать текстовый запрос не только с визуальным содержанием картинки, но и с текстом, который уже находится внутри стикера.

Система должна:

- искать стикеры по описанию объекта, эмоции или ситуации;
- учитывать встроенный текст на стикерах;
- возвращать top-k наиболее релевантных результатов;
- работать на десятках тысяч изображений;
- поддерживать воспроизводимую оценку качества;
- генерировать новый стикер по текстовому запросу и удалять фон.

## 2. Среда и зависимости

Я запускал проект на Python 3.11 через `uv`.

Установка:

```bash
uv sync
```

Основные зависимости зафиксированы в `pyproject.toml` и `uv.lock`, чтобы проект можно было воспроизвести без ручного подбора версий.

Локальные большие артефакты не хранятся в git:

- `data/` - изображения, manifest, embeddings, OCR metadata;
- `models/` - checkpoint SAM;
- `outputs/` - результаты evaluation и generation.

## 3. Данные

Источник данных: открытый датасет `metchee/u-sticker`. Для первичного понимания датасета я также смотрел статью с его анализом: https://arxiv.org/pdf/2502.19108.

Датасет содержит PNG, GIF и WEBM-стикеры, изображения с прозрачным фоном, мемные и персонажные стикеры, а также стикеры с короткими надписями.

В локальной версии после предобработки у меня получился такой индекс:

| Параметр                           | Значение |
| ---------------------------------- | -------: |
| Уникальные стикеры в индексе       |   62 137 |
| Изображения с непустым OCR-текстом |   21 171 |
| Размер основного eval-набора       |      100 |

С данными были несколько практических проблем:

- много дубликатов или почти одинаковых стикеров;
- часть файлов - GIF, поэтому для обработки я беру первый кадр;
- WEBM требует отдельного видеопайплайна, поэтому в текущей версии я его не использовал;
- OCR-текст часто шумный из-за декоративных шрифтов, мемного оформления и низкого разрешения;
- у исходного датасета нет готовой полной relevance-разметки под пользовательские запросы.

## 4. ML-пайплайн

Итоговый пайплайн я разбил на пять стадий.

1. Сбор изображений из локальной директории датасета.
2. Дедупликация через perceptual hash.
3. OCR-разметка изображений через EasyOCR.
4. Построение CLIP image embeddings и CLIP text embeddings для OCR-текста.
5. Поиск с late fusion визуального и OCR-сигнала.

Команды воспроизведения:

```bash
uv run python main.py preprocess --ocr-gpu
uv run python main.py index --device mps
uv run python main.py search --device cpu --query "good morning" --top-k 5
```

На этапе feature extraction для каждого уникального стикера прогоняется CLIP image encoder и сохраняется визуальный embedding. Параллельно результаты EasyOCR фильтруются по confidence threshold, после чего распознанная строка прогоняется через CLIP text encoder. Если OCR-текст отсутствует или confidence слишком низкий, OCR embedding заполняется нулевым вектором, а confidence сохраняется как `0.0`. Это оказалось удобнее, чем хранить разные наборы объектов для визуального и OCR-поиска.

Артефакты индекса:

- `data/embeddings/filenames.json` - порядок файлов в индексе;
- `data/embeddings/image_embeddings.pt` - CLIP image embeddings в формате PyTorch tensor;
- `data/embeddings/ocr_embeddings.pt` - CLIP text embeddings для OCR-строк в формате PyTorch tensor;
- `data/embeddings/ocr_confidences.pt` - confidence OCR для каждого изображения в формате PyTorch tensor;
- `data/embeddings/ocr_metadata.json` - распознанный текст и confidence.

## 5. Архитектура поиска

Визуальные признаки строятся моделью CLIP `ViT-L-14` с pretrained-весами `openai`. Пользовательский запрос кодируется CLIP text encoder, а изображения заранее кодируются CLIP image encoder. Это позволяет делать zero-shot image-text retrieval без обучения модели с нуля.

Для стикеров с текстом используется второй сигнал:

1. EasyOCR извлекает строку из изображения.
2. OCR-текст кодируется CLIP text encoder.
3. OCR-confidence сохраняется как вес надёжности.
4. Во время поиска OCR-score смешивается с visual-score.

Итоговая формула:

```text
final_score = visual_score + ocr_alpha * ocr_confidence^2 * ocr_score
```

Перед fusion оба score нормализуются через z-score. Квадрат confidence нужен, чтобы шумный OCR слабее влиял на выдачу.

FAISS я пока не добавлял: на текущем размере базы точный перебор по векторам занимает около 3-7 мс на CPU, поэтому для проекта и демо этого достаточно. Если расширять базу до сотен тысяч или миллионов объектов, следующим шагом будет FAISS или vector database.

Поиск:

```bash
uv run python main.py search \
  --device cpu \
  --query "good morning" \
  --top-k 5
```

Поиск с отображением результатов:

```bash
uv run python main.py search \
  --device cpu \
  --query "cat waving" \
  --top-k 5 \
  --show
```

## 6. Обоснование выбора методов

Я остановился на CLIP по нескольким причинам:

- он напрямую сопоставляет текст и изображения в общем embedding-пространстве;
- не требует ручной разметки всех стикеров на первом этапе;
- хорошо подходит для прототипа semantic retrieval.

EasyOCR я выбрал вместо Tesseract, потому что на стилизованном тексте стикеров он в моих экспериментах распознавал текст стабильнее. При этом OCR не используется как единственный источник истины: часть стикеров вообще без текста, а часть надписей распознаётся с ошибками.

Late fusion я выбрал вместо раннего объединения признаков, потому что визуальный и OCR-сигнал имеют разную природу и разную надёжность. Ещё плюс в том, что такой подход проще отлаживать: в выдаче можно отдельно смотреть `visual_score`, `ocr_score` и финальный score.

Рассмотренные альтернативы:

| Подход                      | Плюсы                                         | Минусы                                                          |
| --------------------------- | --------------------------------------------- | --------------------------------------------------------------- |
| Keyword search по OCR       | Простая реализация, хороший поиск точных фраз | Не работает для стикеров без текста, чувствителен к OCR-ошибкам |
| Только CLIP image retrieval | Хороший визуальный semantic search            | Плохо учитывает конкретные надписи                              |
| CLIP + OCR late fusion      | Баланс визуального смысла и текста            | Нужно подбирать вес OCR и фильтровать шум                       |
| FAISS/vector DB             | Масштабирование на большие базы               | Пока избыточно для 62k объектов                                 |
| Fine-tuning                 | Потенциально лучшее качество                  | Требует большой ручной relevance-разметки                       |

## 7. Eval-набор и протокол оценки

Для retrieval-задачи выбраны метрики:

- `HitRate@K`: есть ли хотя бы один релевантный объект в top-k;
- `MRR@K`: насколько высоко стоит первый релевантный результат;
- `Recall@K`: какая доля размеченных релевантных объектов найдена;
- `nDCG@K`: учитывает позицию и graded relevance.

Эти метрики подходят, потому что пользователь обычно смотрит первые несколько стикеров. Важно не только наличие подходящего результата, но и его позиция.

Для скорости измеряются:

- p50/p95 полного времени запроса;
- p50/p95 времени scoring.

Оценку я разделил на два набора, потому что одной ручной мини-выборки было бы мало, а полностью размеченного датасета для этой задачи нет.

1. Основной OCR-eval: 100 запросов, автоматически собранных из OCR metadata с confidence >= 0.75. Это стресс-тест текстовой части retrieval.
2. Demo-eval: 5 ручных сценариев, покрывающих visual, OCR, mixed и fallback-запросы.

Основной eval формируется скриптом [cli/build_eval.py](/Users/dlifantyev/prsnl/sticker-suggest/cli/build_eval.py). Скрипт читает `data/embeddings/ocr_metadata.json`, где для каждого файла хранится распознанный текст и confidence EasyOCR. Дальше применяется несколько фильтров:

- берутся только OCR-строки с confidence не ниже `0.75`;
- текст нормализуется: приводится к нижнему регистру, из него оставляются только буквенно-цифровые токены;
- отбрасываются слишком короткие строки, полностью цифровые строки и очевидно шумные фразы;
- используется небольшой blocklist для нежелательных фраз, потому что в исходных мемных стикерах такие тексты встречаются;
- для одного запроса ограничивается максимальное число релевантных файлов, чтобы частые OCR-фразы не доминировали в метриках.

После фильтрации скрипт выбирает 100 запросов с фиксированным `seed=42`. Это делает набор стабильным: при одинаковых OCR metadata команда создаёт один и тот же `eval/queries.jsonl` и `eval/qrels.jsonl`.

Qrels строятся автоматически. Для каждого выбранного запроса релевантными считаются изображения, у которых нормализованный OCR-текст совпадает с запросом. Им присваивается relevance `2`. Это не идеальная ручная разметка, но такой набор хорошо проверяет именно способность находить стикеры по тексту внутри изображения. Поэтому отдельно сохранён `demo-eval` из 5 ручных сценариев: он нужен для показа visual, OCR, mixed и fallback-кейсов.

Пересборка основного eval:

```bash
uv run python main.py build-eval \
  --size 100 \
  --seed 42 \
  --min-confidence 0.75 \
  --max-relevant 12
```

Основной прогон:

```bash
uv run python main.py evaluate \
  --device cpu \
  --top-k 10 \
  --ocr-alpha 0.01 \
  --output outputs/evaluation/metrics.json
```

Сравнение с baseline без OCR-сигнала:

```bash
uv run python main.py evaluate \
  --device cpu \
  --top-k 10 \
  --ocr-alpha 0.0 \
  --output outputs/evaluation/metrics_image_only.json
```

Оценка ручного demo-набора:

```bash
uv run python main.py evaluate \
  --device cpu \
  --top-k 10 \
  --queries eval/demo_queries.jsonl \
  --qrels eval/demo_qrels.jsonl \
  --output outputs/evaluation/metrics_demo.json
```

## 8. Результаты

Основной OCR-eval, `top_k=10`:

| Режим                              | HitRate@10 | MRR@10 | Recall@10 | nDCG@10 |
| ---------------------------------- | ---------: | -----: | --------: | ------: |
| Image-only, `ocr_alpha=0.0`        |      0.650 |  0.533 |     0.640 |   0.557 |
| Финальный fusion, `ocr_alpha=0.01` |      0.650 |  0.534 |     0.640 |   0.557 |
| OCR-heavy, `ocr_alpha=0.2`         |      0.710 |  0.575 |     0.700 |   0.603 |
| OCR-heavy, `ocr_alpha=1.0`         |      0.760 |  0.667 |     0.753 |   0.686 |

Latency для финального режима на CPU:

| Показатель  | Значение |
| ----------- | -------: |
| total p50   |  37.5 ms |
| total p95   |  71.2 ms |
| scoring p50 |   4.0 ms |
| scoring p95 |   7.1 ms |

Demo-eval из 5 ручных сценариев при `ocr_alpha=0.01`:

| Метрика     | Значение |
| ----------- | -------: |
| HitRate@10  |    1.000 |
| MRR@10      |    1.000 |
| Recall@10   |    1.000 |
| nDCG@10     |    0.922 |
| total p50   |  29.0 ms |
| total p95   |  31.3 ms |
| scoring p50 |   3.4 ms |
| scoring p95 |   5.9 ms |

При `ocr_alpha=1.0` на demo-eval качество падает до HitRate@10 = 0.200 и nDCG@10 = 0.061. Для меня это был главный сигнал, что нельзя просто сильно увеличить вес OCR. Высокий OCR-вес улучшает OCR-стресс-тест, но может портить визуальные и смешанные запросы из-за шумного OCR. Поэтому в финальной конфигурации оставлен консервативный вес `ocr_alpha=0.01`.

## 9. Анализ ошибок

После просмотра результатов я выделил несколько основных типов ошибок.

1. Шумный OCR. EasyOCR иногда распознаёт бессмысленные фрагменты или искажает слова. Такие запросы попадают в OCR-eval, но плохо соответствуют реальным запросам.
2. Конфликт визуального и текстового сигналов. Если OCR-score получает большой вес, система начинает искать похожие строки, а не похожие стикеры.
3. Стилизованные надписи. Декоративные шрифты, обводки и низкое разрешение ухудшают OCR.
4. Дубликаты и похожие варианты. Даже после perceptual hashing в базе остаются близкие изображения, которые могут вытеснять более разнообразные результаты.
5. Неполная разметка. Основной eval автоматически построен из OCR metadata, поэтому он хорошо проверяет текстовую часть, но не является полной независимой relevance-разметкой.

Численно в основном OCR-eval при финальном `ocr_alpha=0.01` 35 из 100 запросов не имели релевантного объекта в top-10. При `ocr_alpha=1.0` число таких промахов снижается до 24, но ручной demo-набор резко деградирует. Это подтверждает, что нужен отдельный tuning-набор с ручной разметкой визуальных, текстовых и смешанных запросов.

## 10. Генерация стикеров

Генерация вынесена в отдельный модуль `src/generation/`.

Схема:

1. SDXL Turbo генерирует изображение по prompt.
2. Prompt ограничивает модель: один центрированный объект, белый фон, без текста и лишних объектов.
3. SAM сегментирует основной объект по центральному bounding box.
4. Маска превращается в alpha channel.
5. Добавляется белая sticker-style обводка.
6. Результат сохраняется как PNG.

Перед финальным вариантом я пробовал разные prompt-шаблоны для diffusion-модели. Простые запросы вроде `cat waving sticker` часто давали не один объект, а сцену, набор маленьких стикеров, лишние лица или декоративный фон. Для задачи это неудобно: затем SAM сложнее выделяет главный объект, а результат хуже выглядит как отдельный стикер.

Текущий prompt:

```text
A single isolated sticker of {query}. Exactly one main subject, centered in the image, full body visible. No other characters, no extra faces, no icons, no repeated objects, no sticker sheet, no collage, no background elements. Plain white background, clean outline, simple composition.
```

Negative prompt:

```text
multiple characters, many objects, sticker sheet, collage, grid, icons, repeated faces, extra heads, extra people, background scene, decorations, text, letters, watermark, logo, clutter, cropped body, cut off
```

Такой prompt engineering оказался важен именно для последующей постобработки: чем проще фон и чем яснее один главный объект, тем стабильнее SAM строит маску и тем меньше артефактов остаётся после удаления фона.

В качестве альтернативы я рассматривал FLUX. Потенциально он мог дать более высокое визуальное качество и лучше следовать текстовому запросу, но локально не получилось стабильно запустить его из-за размера модели и требований к памяти. Поэтому для итоговой версии выбрана SDXL Turbo: качество может быть ниже, чем у FLUX, зато модель реально запускается локально, быстрее подходит для демо и лучше соответствует требованию воспроизводимости.

Генерация отдельного стикера:

```bash
uv run python main.py generate \
  --query "cat waving sticker" \
  --output outputs/generated/cat_waving.png \
  --generation-device mps
```

Fallback в поиске:

```bash
uv run python main.py search \
  --query "spiderman kissing a cat" \
  --top-k 10 \
  --generate-on-low-score \
  --min-score 4.0 \
  --generation-device mps \
  --preload-generator blocking \
  --show
```

Сейчас fallback использует простое правило: если нижний результат в top-k ниже порога, генерируется дополнительный вариант. Порог не является вероятностью релевантности, его в будущем нужно калибровать на ручной оценке.

## 11. Пути доработки

Что я бы доработал дальше:

- собрать ручной validation set из 100-200 пользовательских запросов с relevance;
- использовать FAISS при росте базы;
- добавить reranker для top-50 результатов;
- калибровать порог fallback-генерации по ручной оценке;
- добавить evaluation для сгенерированных стикеров.

## 12. Выводы

В итоге получился полный ML-пайплайн: предобработка данных, OCR, CLIP embeddings, retrieval, evaluation, generation и демонстрация. Система работает на базе из 62 137 стикеров и выполняет точный scoring за единицы миллисекунд на CPU.

Главный практический вывод: для стикеров нужен мультимодальный подход. Один CLIP хорошо ищет визуальный смысл, но не всегда учитывает надписи. Один OCR слишком шумный и не работает для изображений без текста. Late fusion даёт управляемый компромисс, а анализ `ocr_alpha` показывает, почему вес OCR нужно подбирать аккуратно.
