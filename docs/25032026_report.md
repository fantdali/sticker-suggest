# Отчет по рубежному контролю

## Проект: Интеллектуальная система подбора стикеров и открыток

## 1. Введение

Цель проекта — разработать систему, которая по текстовому запросу подбирает релевантные стикеры из базы. Cистема должна учитывать не только текст запроса, но и визуальную семантику изображений, а также встроенный текст внутри самих изображений. В полном варианте проекта дополнительно предполагается генерация нового стикера, если в базе отсутствуют подходящие результаты.

Задача относится к мультимодальному поиску, поскольку необходимо сопоставлять текстовый запрос пользователя с визуальным содержимым изображений. В ряде случаев с текстом внутри изображений. Это особенно важно для стикеров, содержащих короткие надписи вроде "hello", "good morning", "happy birthday" итд.

Требования к системе на текущем этапе:

- поддержка поиска по текстовому описанию;
- учет визуального содержания изображения;
- учет встроенного текста в изображениях;
- возможность масштабирования на датасет размером от 10k изображений и выше;
- дальнейшая возможность расширения до генеративного режима.

Ограничения:

- поиск открытого датасета стикеров с аннотациями и текстовыми описаниями;
- изображения содержат шум, дубликаты и различные форматы файлов;
- некоторые объекты представлены в виде GIF/WEBM, что усложняет обработку;
- встроенный текст часто оформлен декоративными шрифтами, из-за чего классический OCR работает нестабильно;

---

## 2. Постановка задачи и сценарий использования

Юзер водит текстовый запрос, например:
"stitch",
"hello sticker",
"good morning",
"cat says hi".

Система должна:

1. преобразовать запрос в векторное представление;
2. найти в базе наиболее релевантные изображения;
3. учитывать как визуальное содержание изображения, так и встроенный текст;
4. выдать top-k наиболее подходящих результатов.

В финальном виде система должна уметь переходить в режим генерации нового стикера в случае, если релевантные изображения в базе отсутствуют или имеют слишком низкий скор.

---

## 3. Описание датасета

В качестве основы датасета использовался открытый датасет стикеров [`metchee/u-sticker`](https://huggingface.co/datasets/metchee/u-sticker).

### Структура данных

У датесета есть хорошая статья с анализом данных в нем https://arxiv.org/pdf/2502.19108.

Датасет содержит:

- изображения в форматах PNG, WEBM, GIF;
- изображения с прозрачным фоном;
- изображения с текстом и без текста;
- различные визуальные стили: персонажи, мемные стикеры, итд;
- контекст диалогов, в которых эти стикеры используются для части данных.

### Ограничения

1. **Дубликаты**  
   В датасете присутствуют одинаковые изображения с разными именами или идентификаторами. Это ухудшает качество поиска, так как один и тот же объект может многократно попадать в top-k.

2. **GIF/WEBM файлы**  
   При OCR-обработке GIF-файлы приводили к резкому росту потребления памяти, так как содержат несколько кадров. Для корректной работы OCR брал только первый кадр. WEBM файлы отбросил, так как их обработка требует более сложного пайплайна.

3. **Встроенный текст**  
   Существенная часть изображений содержит текст. Это важно для сценариев поиска по фразам.

4. **Стилистически сложный текст**  
   Надписи часто выполнены декоративными шрифтами, разными формами итд. Это осложняет OCR.

5. **Объем**  
   Датасет содержит 370k стикеров, 100k уникальных. В рамках ограниченных ресурсов и времени решил работать с подмножеством из рекомендованных 10k изображений, отобранных случайным образом.

## 4. Предварительный анализ данных

### 4.1. Просмотр и визуальная инспекция

Была проведена ручная визуальная проверка примеров изображений из датасета. Форматы данных. Наличие текста.

### 4.2. Наличие текста

Для оценки наличия текста был протестирован OCR-подход. Сначала использовался Tesseract, однако он показал низкое качество на стилизованном тексте. Затем был протестирован EasyOCR, который оказался существенно лучше на мультяшных надписях. Остановился на EasyOCR.

### 4.3. Качество OCR

- текстовый OCR-сигнал сильнее всего полезен для запросов с явной текстовой компонентой;
- текст может быть распознан с ошибками или распознан, когда его нет. На 40% изображений из подвыборки в 1k был распознан какой-то текст. Построены гистограммы распределения средней длины текстов;
- OCR-confidence может служить полезным признаком для взвешивания OCR-сигнала. Построены гистограммы распределения confidence. Построены примеры изображений с высоким и низким confidence.

### 4.4. Дубликаты

Удалилил дубликаты на основе perceptual hashing, чтобы улучшить разнообразие top-k результатов. Всего из 10k было удалено около 1.5k дубликатов.

### Выводы

1. База подходит для задачи поиска стикеров по описанию.
2. Встроенный текст встречается достаточно часто, чтобы учитывать его в системе.
3. Нужен мультимодальный подход: только OCR недостаточен, только image embeddings тоже недостаточны.
4. Необходим этап очистки данных.

## 5. Формирование признаков

Выбраны два типа признаков: визуальные и текстовые.

### 5.1. Визуальные признаки

Для извлечения визуальных признаков была выбрана мультимодальная модель CLIP. Отображает изображения и тексты в общее embedding-пространство, в котором можно напрямую сравнивать текстовый запрос и изображение.

Почему CLIP подходит для задачи:

- позволяет выполнять image-text retrieval без отдельного обучения на первом этапе;
- удобно использовать для быстрого прототипирования semantic search;

В работе использовались image embeddings для каждого изображения из базы и text embedding для пользовательского запроса. Оба embedding'a получались через CLIP.

### 5.2. Текстовые признаки из изображения

Поскольку часть стикеров и открыток содержит встроенный текст, в качестве второго типа признаков использовался OCR.

Пайплайн:

1. изображение подается в OCR-модель;
2. из изображения извлекается строка текста;
3. для этой строки строится text embedding через тот же text encoder CLIP;
4. этот embedding используется как дополнительный источник сигнала при поиске;
5. дополнительно OCR-confidence используется для взвешивания этого сигнала.

Почему это важно:

- позволяет улучшить поиск по запросам с конкретными словами;

## 6. Обоснование выбранного подхода

На текущем этапе выбран retrieval-подход на основе семантических embeddings.

### Общая идея

1. Для каждого изображения вычисляется визуальный embedding.
2. Дополнительно вычисляется OCR-text embedding.
3. Пользовательский запрос кодируется text encoder'ом.
4. Поиск выполняется через similarity между запросом и объектами базы.
5. Итоговый score строится как комбинация визуального score и OCR score.

### Почему такой подход подходит

- напрямую соответствует постановке задачи семантического поиска по базе изображений;
- легко масштабируется на десятки тысяч изображений;
- не требует обучения модели с нуля;
- хорошо поддерживает последующий переход к vector database поиску.

### Почему не keyword search

Поиск только по OCR-тексту не подходит, так как:

- многие изображения вообще не содержат текст;
- OCR может ошибаться;
- юзер часто ищет не слова, а смысл или визуальный стиль.

### Почему не только image embeddings

Поиск только по визуальным embeddings также недостаточен, потому что:

- текст внутри изображений является значимой частью семантики;
- запросы типа "hello sticker" или "happy birthday card" требуют учета самой надписи, а не только визуального стиля.

### Схема fusion

На текущем этапе используется late fusion:

- similarity между query и image embedding;
- similarity между query и OCR-text embedding;
- оба скора нормализуются для сопоставимости;
- OCR-score дополнительно взвешивается по confidence.

## 7. Метрики качества

Для первого этапа полноценная количественная оценка не делалась. Были проведены качественные эксперименты - визуальный просмотр top-k результатов по нескольким запросам. После них замечено и исправлено влияние дубликатов; введена нормализация двух скоров; оценено влияние OCR-confidence и веса для OCR-score.

Для финального этапа неплохо было бы ввести формальный eval. Для этого можно выделить подвыборку исходного датасета и собрать небольшой набор текстовых запросов с целью получить предполагаемые релеватные стикеры. Вручную разметить релевантность top-k результатов для каждого запроса. На основе этой разметки можно посчитать следующие метрики: Recall@K, HitRate@K, MRR.

### Почему именно эти метрики

Эти метрики подходят для retrieval-задач, где важны:

- наличие релевантного объекта в top-k;
- позиция первого хорошего результата;

## 8. План дальнейшей работы

На следующем этапе планируется:

1. **Датасет**

- стабилизировать финальный preprocessing pipeline.
- возможно расширить базу для более богатого поиска.

2. **Automation**

- финализировать и оптимизировать этап получения признаков;

3. **Быстрый поиск**

- перейти от полного перебора к FAISS или vector DB, хотя на объемах в 10k это не критично.

4. **Подготовка eval**

- собрать небольшой набор текстовых запросов;
- вручную разметить релевантность top-k результатов;
- посчитать HitRate@K, MRR.

5. **Реализация генерации**

- выбрать генеративную модель для sticker generation;
- реализовать background removal;
- определить критерий перехода в режим генерации.

6. **Финал**

- подготовить демонстрацию.
